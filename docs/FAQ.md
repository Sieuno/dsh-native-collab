# 常见问题 (FAQ)

## 为什么新版不再有独立的 Team 面板和「身份互转」功能？

从 DSH `0.2.2-rc.2` 起，官方已经深度整合了 Team 与 Subagent：所有成员统一基于 Subagent 树进行管理，官方原生自带了团队成员发现、任务看板和会话 Team 开关。

因此，本插件不再重复造轮子去替换官方的团队管理与通信服务，而是完全复用官方原生面板与底层架构。原有的“身份互转”已由官方统一的成员体系取代。本插件提供模型来源选择和防止死循环的自动消息额度，并优化委派提示词。

## 设置修改后如何保存？为什么没有之前的自动保存提示？

进入 DSH 的「插件 → 已安装」，打开本插件的详情页即可看到设置表单（包含「Subagent 模型来源」、「自动唤醒消息上限」与「禁用 Agent 等待工具」三项设置）。

新版使用官方表单组件与配置服务，调整选项后点击底部的「保存」按钮，保存成功后即刻对后续工具调用生效。这替代了旧版容易产生并发保存冲突的逐项自动保存机制。

> [!NOTE]
> 如果是在插件管理器中**启用或禁用整个插件**，需要完全重启该 Profile 的 DSH 实例方可生效。

## 为什么要提供「禁用 Agent 等待工具」开关？

DSH 原生的 `wait_agent` 工具常被 Agent 用作主动等待或轮询子任务，但这往往会导致父 Agent 占用不必要的对话轮次，并在等待期间空耗上下文 Token。

实际上，DSH 官方内置了子 Agent 任务完成自动通知机制——父 Agent 在派发任务后主动结束当前回复，等子 Agent 完成时就会被官方通知自动唤醒继续执行。

开启「禁用 Agent 等待工具」后，插件会对 Agent 隐藏 `wait_agent` 工具，并在提示词中引导 Agent 派发任务后主动结束当前轮次、静待官方唤醒。这既避免了死等轮询，又能显著节省 Token 和轮次（默认保持关闭，可按需开启）。

## 之前的直属子 Agent 通信限制开关去哪了？

新版移除了旧版「允许向正在工作的子 Agent 发送指导」和「允许向空闲子 Agent 发送消息」等额外的通信限制开关。

协作树内 Agent 之间的消息通信完全回归官方原生标准行为，避免冗余的配置门禁阻断正常的任务协同。旧配置中若仍残留这些历史开关，插件会自动兼容并忽略，不会阻止消息发送。

## 模型来源选择「官方默认策略」是什么意思？

创建子 Agent 时沿用 DSH 官方的会话模型授权策略。模型选择和会话复制（fork）的继承规则仍然可用；这也是插件的默认选项。

## 当自动消息达到额度上限时，Agent 会被终止吗？

**不会终止 Agent。**

当消息额度达到上限时，仅仅是拒绝发送当前的自动消息，Agent 依然保持运行。额度机制的设计初衷是防止自主协作陷入无限死循环：
- 只要用户在对话框中输入任意新内容或回复提问，全协作树的额度都会**立即自动清零重置**；
- 子 Agent 任务执行完成后，向直属父级汇报结果（携带 `task_result: true`）**不计入额度**；
- 官方原生的任务完成系统通知同样不计入额度；
- 发送失败时会自动退还所扣减的额度。

## 为什么不再提供模型侧 `queue` 投递选项？

新版插件统一复用官方 `send_message` 的 `steer` 投递：正在工作的目标在步骤边界接收消息，空闲目标可以开始新轮次，不强制中断当前模型请求或工具调用。

旧版 `queue` 表示把消息排队到后续轮次，并非强制插队。这次是本插件主动移除模型侧的 `delivery` 选择，不代表官方废弃了 `queue`；官方用户侧投递仍支持排队。向新版模型工具传入旧 `delivery` 参数会收到错误提示。

## 子 Agent 能唤醒父级吗？

可以。这里的“父级在线”指父 Agent 实例仍由宿主加载，空闲也算在线：

- **父级只是空闲或结束当前轮次**：自动完成通知可以唤醒它，开始新轮次；正在工作的父级则在步骤边界接收通知。
- **父实例已经释放**：自动完成通知不会为了回报结果而冷恢复它。多层委派中，中间的子 Agent 可能先结束并被释放，而它创建的后代仍继续工作。
- **显式发送 `send_message`**：只要协作树根（Lead）仍被宿主加载、目标仍属于同一棵树且支持继续执行，官方可以冷恢复已释放的父会话再投递消息。这与自动完成通知的行为不同。

因此，结束当前轮次等待结果是正常做法，不需要让父级一直生成或轮询来保持可唤醒。

## 升级或卸载插件后，如果 DSH 启动异常该怎么办？

如果升级或卸载后遇到 DSH 启动报错，通常是因为旧版本的补丁配置（startup patch）有残留。请按照以下步骤排查清理：
1. **完全退出 DSH** 进程，并备份您的 Profile 配置目录；
2. 打开该 Profile 目录下的 `cordis.patch.yml`（以及启动器生成的 `*.patch.json` 文件）；
3. 检查文件中是否包含对 `@sieuno/dsh-native-collab` 或旧版子路径（如 `/subagent`、`/agent-team`）的残留引用；
4. **仅删除涉及本插件的失效覆盖条目**，保留其他插件和基础配置不变（切勿直接清空整个文件）；
5. 保存后重新启动 DSH，检查官方协作服务是否恢复；若仍启动失败，保留具体错误信息，继续排查其他配置或依赖问题。
