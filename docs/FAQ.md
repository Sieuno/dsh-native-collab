# 常见问题 (FAQ)

## 安装后如何启用功能？

进入插件管理页面按需配置即可。子智能体设置和增强偏好均会自动读取、修改后自动保存；普通保存不需要离线迁移，也不会热迁移运行中的 Agent。需重启生效的设置按提示正常重启同一 Profile 即可（仅刷新浏览器网页不算重启）。

## 保存设置后，为什么当前对话没有立即变化？

功能增强主开关及连续自动唤醒轮数上限属于启动配置，在重启同一 Profile 后对新会话或新轮次生效；模型来源设置则用于之后的模型查询与 Agent 创建，不会中途更改正在执行任务的 Agent。连续自动唤醒计数存储在进程内存中，进程重启后自动清零。

## 为什么原生子智能体页面没有运行限制？如何修改？

增强入口接管后，原生服务条目处于禁用状态，原生页面可能只显示模型选择。请在本插件设置页的“子智能体设置”中修改；进入页面自动读取，合法修改后自动保存。它读取宿主合成的原生配置，并将修改写回当前 Profile 的 `subagent` 条目，不另存一份插件配置。

默认递归深度为 1、并行上限为 8。深度 0 禁止继承此值的工具委派，工具显式深度仍优先；并行上限统计同一根 Agent 下所有递归层级存活和创建中的子级，不计根 Agent。修改用于后续准入，调低上限不会停止已有子级。连续自动唤醒轮数是另一项独立限制。

保存会校验版本并保留其他配置。检测到更高优先级覆盖、目标不明确或并发修改时拒绝保存；先保留草稿并重新读取，核对覆盖来源后再操作，不要同时启用原生与增强服务来恢复界面。

## 如何临时关闭 HMR 开发热重载？

这是可选的本地调试操作，仅关闭 DSH 自身的热重载，不影响协作插件：

```yaml
- id: hmr
  disabled: true
```

将上述内容合并入实际 Profile 的 `cordis.patch.yml` 并重启即可。

## 三种模型来源有什么区别？

- **对话开始时设置的子模型可用列表（原生设置）**：沿用会话创建时锁定的候选模型快照。
- **DSH当前设置的子模型可用列表**：每次创建或查询时，动态读取原生设置中当前勾选的模型。
- **当前DSH所有可用模型**：读取当前 DSH 注册的全部可用模型（仍受对应模型适配器及账号权限约束，不会绕过安全检查）。

## 单一管理入口与原生服务如何切换？

插件 Patch 只插入一个管理入口统一管理后台。入口启用时运行托管服务；若关闭管理入口并重启 Profile，系统会自动切回原生服务。预设工具在内存中按预设 ID 适配，不修改预设配置文件，未知自定义 provider 不受影响。

## 误卸载后 DSH 无法启动，如何修复？

本条仅适用于此前曾手动将插件内部模块 pin 到底层配置文件、导致卸载后找不到模块的异常排查。普通安装与卸载无需手动修改配置。

1. 停止 DSH 服务：彻底停止 DSH 服务进程，保留现有配置、会话和额度记录。
2. 手动修复实际 Profile：打开对应 Profile 的配置文件（如 `cordis.patch.yml` 或 `cordis.yml`），移除所有指向已卸载 `@sieuno/dsh-native-collab` 模块的遗留引用；恢复原生根服务与预设工具。同时检查该 Profile 目录下的 `*.patch.json` 外部启动覆盖文件，其中残留的插件行同样会导致启动失败，见下一节。
3. 不要清空整个 patch：请仅移除遗留的失效条目，不要清空整个 patch，不要删除会话或用量记录。四个根层工具仍应保持禁用。修复完成后重新启动 DSH 即可。

## 启动失败，且存在外部启动覆盖文件时怎么处理？

外部启动覆盖文件（Profile 目录下由本机启动器生成的 `*.patch.json`，例如 `desktop-next.cordis.patch.json`、`desktop-next.runtime.patch.json`）优先级高于 Profile 的 `cordis.patch.yml`。插件被卸载、禁用或换版本后，这些文件里残留的模块行会让 DSH 直接启动失败。按顺序处理：

1. **完全停止 DSH 进程**，不要只关网页；保留配置、会话和用量记录。
2. **备份**：把可疑的 `*.patch.json` 覆盖文件和 Profile 的 `cordis.patch.yml`（或 `cordis.yml`）复制一份，或就地改名为 `*.bak` 以便回退。
3. **删除覆盖文件中的插件行**：在每份 `*.patch.json` 中查找 `@sieuno/dsh-native-collab` 及其子路径（`/subagent`、`/agent-team`、`/tool-*`）与 `dsh-native-collab-ui`，整行删除；不确定是哪一份时，先把可疑文件改名备份，逐份恢复启动确认。
4. **检查 Profile patch**：同样移除上述残留行；根层 `subagent`、`agent-team`、`tool-agent-team` 三个原生服务应恢复可用，四个根层工具保持禁用。不要清空整份 patch。
5. **重启同一 Profile** 并确认会话可以打开。若仍失败且插件尚在，把管理入口行 `dsh-native-collab-ui` 的 `disabled` 改为 `true` 再重启，先回到原生服务，然后按上一节步骤处理。
6. **反馈**：提供 DSH、Node 与插件版本、错误码和脱敏后的相关配置行；不要上传整套 Profile 或含凭据的文件。

## 连续自动唤醒轮数上限是什么？超限后如何恢复？

默认上限为连续自动唤醒 32 轮，由会话所有 Agent 共享，旨在防止多 Agent 协作时陷入无休止的死循环。
- **只计无人类介入**：仅统计无用户输入参与的连续跨会话自动唤醒与消息。
- **重置机制**：任一相关 Session 收到用户输入即刻清零；进程重启也会清零，计数仅在内存中。
- **超限行为**：达到上限时仅向尝试发送消息的 Agent 报错 `Automatic wake limit reached; message send failed.`，不会取消任何 Agent。向父级或 Team Lead 自动回报任务完成或停止结果不受此限。
- **恢复方法**：用户在相关会话中发送任意一条消息，即可重置计数并恢复交互。

## 如何提交反馈？

请提供 DSH、Node 及插件版本号、脱敏后的配置信息、复现步骤及错误日志。请务必遮蔽 Token、API Key、私人路径及对话隐私，不要上传整套配置或会话记录。
